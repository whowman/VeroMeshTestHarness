# How closely each mock follows the platform's public API

Every simulated system mocks the platform's **public, documented API**: the same paths, parameters, paging, sign-in flow, response shapes and error forms that a connector meets at a customer. A connector built against the harness should need only a base URL and credentials changed to run against the real system.

Each mock implements the part of the API a VeroMesh connector reads (read-only), and simplifies the rest. Each row below names the documentation followed, what is covered, and what is simplified. Checked on 22 November 2026.

| System | Public API followed | What the mock covers | What it simplifies |
| --- | --- | --- | --- |
| Microsoft Entra ID | Microsoft Graph v1.0: [users](https://learn.microsoft.com/graph/api/user-list), [user delta](https://learn.microsoft.com/graph/api/user-delta), [delta query](https://learn.microsoft.com/graph/delta-query-users), [manager](https://learn.microsoft.com/graph/api/user-list-manager), groups, service principals | `/v1.0/users` with `$select`, `$filter` (`eq`, `startswith`), `$top`, `$expand=manager` (with a nested `$select`), `@odata.nextLink`; `users/{id}`, `manager`, `memberOf`; `groups` and `members`; `servicePrincipals` and `owners`; `users/delta` with `$skiptoken`, `@odata.deltaLink` and `@removed` for deleted users; OAuth 2.0 client credentials at `/{tenant}/oauth2/v2.0/token` | The token is a fixed string, not a signed JWT; `$filter` covers `eq` and `startswith` joined by `and`; the delta token is readable, not opaque; `$expand` covers only `manager` on the users list (no `$levels`); no `$count` or batching |
| SharePoint | Microsoft Graph v1.0: sites, drives, [driveItem children](https://learn.microsoft.com/graph/api/driveitem-list-children), [download content](https://learn.microsoft.com/graph/api/driveitem-get-content), driveItem delta | `/v1.0/sites?search=`, `sites/{id}`, `sites/{id}/drive`, `drives/{id}/root/children`, `items/{id}/children`, `items/{id}`; `items/{id}/content` answers **302 Found** to a pre-authenticated download URL, as Graph does; `root/delta` | Documents are markdown (`text/markdown`), not Word or PDF; one folder level; the delta token is a timestamp |
| ServiceNow | [Table API](https://www.servicenow.com/docs/r/api-reference/rest-apis/c_TableAPI.html) | `GET /api/now/table/{tableName}` and `/{sys_id}`; `sysparm_query` (`=`, `!=`, `>`, `>=`, `<`, `<=`, `LIKE`, `STARTSWITH`, `ISEMPTY`, `ISNOTEMPTY`, `^`, `^OR`, `ORDERBY`, `ORDERBYDESC`), `sysparm_fields`, `sysparm_display_value` (`true`, `all`), `sysparm_limit` and `sysparm_offset`; `X-Total-Count` and the `Link` header; reference fields as `{link, value}`; basic auth or an OAuth token from `/oauth_token.do` | Ten tables (users, departments, groups and members, business applications, servers, database instances, CI relationships, incidents, change requests); no dot-walking in queries; no `sysparm_exclude_reference_link` |
| Workday HCM | Workday REST API (`/ccx/api/v1/{tenant}`) and Reports as a Service (`/ccx/service/customreport2/{tenant}/{owner}/{report}?format=json`), as documented in Workday Community (sign-in required) and by integration vendors ([Workato](https://docs.workato.com/connectors/workday/workday_raas), [Prismatic](https://prismatic.io/docs/components/workday/)); OAuth at `/ccx/oauth2/{tenant}/token` | `workers` (`limit`, `offset`, `search`, `total`/`data`), `workers/{id}`, `supervisoryOrganizations`; two custom reports in RaaS JSON (`Report_Entry`), a worker report and a changes report by date entered; OAuth with a refresh token or client credentials | The full documentation needs a Workday Community sign-in, so the worker fields follow the published examples and are a subset. The reports are VeroMesh's own custom reports, so their fields are ours to define. No SOAP (Human Resources web service) and no WQL. Check against a real tenant when a design partner has one |
| Databricks | [Unity Catalog REST](https://docs.databricks.com/api/uc-tables/v1/list-tables), the [lineage system tables](https://docs.databricks.com/admin/system-tables/lineage.html) and [lineage REST API](https://docs.databricks.com/aws/data-governance/unity-catalog/data-lineage), the [Statement Execution API](https://docs.databricks.com/api/statement-execution/v1/execute-statement), [`information_schema.column_tags`](https://learn.microsoft.com/azure/databricks/sql/language-manual/information-schema/column_tags) | `/api/2.1/unity-catalog/catalogs`, `schemas`, `tables` (with `next_page_token`), `tables/{full_name}`; `/api/2.0/lineage-tracking/table-lineage`; `POST /api/2.0/sql/statements` answering `JSON_ARRAY` inline for `system.access.table_lineage`, `system.information_schema.column_tags` and `table_tags`, and `SELECT * FROM <table> LIMIT n`; a personal access token or OAuth M2M at `/oidc/v1/token` | SQL is only the statements above, answered synchronously; no column lineage; tags are one `classification` tag per column. Databricks documents the system tables as the main route for lineage, with the REST endpoint as an alternative |
| Oracle Fusion Cloud ERP | REST API for Oracle Fusion Cloud Financials: [invoices](https://docs.oracle.com/en/cloud/saas/financials/25c/farfa/op-invoices-get.html), [invoice approvals and notifications history](https://docs.oracle.com/en/cloud/saas/financials/25d/farfa/api-invoice-approvals-and-notifications-history.html), suppliers, purchase orders; HCM user accounts | `/fscmRestApi/resources/11.13.18.05/invoices`, `invoiceApprovalsAndNotificationsHistory` (who approved, by ERP user name), `suppliers`, `purchaseOrders`; `/hcmRestApi/resources/11.13.18.05/userAccounts` with its `userAccountRoles` child (`expand=userAccountRoles` or `/userAccounts/{GUID}/child/userAccountRoles`; role codes, no names); `limit`, `offset`, `hasMore`, `count`, `totalResults=true`, and `q` (`Field op value;...`); basic auth | A subset of each resource's attributes; no `fields` or finders, and `expand` and child resources only for user account roles; purchase orders carry their buyer and approver as person numbers (Oracle keeps the approval history in a separate purchasing history resource) |
| EMR | [HL7 FHIR R4](https://hl7.org/fhir/R4/PractitionerRole.html): Organization, Practitioner, PractitionerRole, Patient, Encounter, MedicationRequest, searchset Bundles, CapabilityStatement; the identifier systems an Epic FHIR server uses (NPI `http://hl7.org/fhir/sid/us-npi`) | `/fhir/{type}` searches with `_count`, `_offset`, `identifier` (`system|value`), `active`, `practitioner`, `subject`/`patient`, `_lastUpdated` (`gt`, `ge`, `lt`, `le`), `_id`; `/fhir/{type}/{id}`; `/fhir/metadata`; a `next` link; a client-credentials token standing in for SMART Backend Services | No signed-JWT client assertion (SMART Backend Services uses one); no `_include`, chained searches or `_revinclude`; privileges are a local code system (`urn:kestrel:privilege`) |
| Semantic layer | [Stardog HTTP API](https://docs.stardog.com/developing/http-api): the [SPARQL endpoint](https://docs.stardog.com/query-stardog/) `/{db}/query`, `/admin/databases` | SPARQL 1.1 queries by GET (`?query=`) or POST (form-encoded or `application/sparql-query`), answered as `application/sparql-results+json`; basic auth | Read-only (updates are refused); no reasoning, transactions or virtual graphs |
| dbt | [dbt artifacts](https://docs.getdbt.com/reference/artifacts/dbt-artifacts): `manifest.json` (v12), `run_results.json` (v6), `catalog.json` | Sources and models with `depends_on`, columns with `meta`, tests; the last run's statuses | Served over HTTP for convenience (dbt writes them as files); a subset of each artifact's fields |

## Keeping it faithful

- **Before relying on a field, check it.** Connectors should read only fields in the platform's documentation. Where this page says a mock simplifies something, the connector should handle the full form too.
- **Check against a real sandbox when one exists.** A ServiceNow developer instance, an Entra ID developer tenant, Databricks Free Edition and a FHIR sandbox are all free. Running a connector against the mock and the sandbox and comparing the results catches what documentation alone misses.
- **Workday needs a real tenant.** Its documentation and sandboxes are open only to customers and partners, so the Workday mock should be checked against the design partner's tenant once they sign.
- **When a platform changes its API**, update the mock and this page in the same pull request.
